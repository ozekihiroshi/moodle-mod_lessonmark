## 1. 目的と位置づけ

**それぞれ単独で価値があり、組み合わせると学習体験がさらに良くなる。**

`mod_lessonmark`、`format_duallearning`、`theme_duallearning` の変更は、この原則に照らして設計する。検査への合格だけでなく、単独で成立すること、責務が適切であること、連携によって具体的な利点が生まれることを判断する。

本書は3プラグイン間の責務と連携に関する開発指針である。個々の製品仕様を置き換えたり、現在の実装が全項目を満たすと宣言したりするものではない。既存実装との隔たりは課題として記録し、変更に関係する範囲から改善する。仕様と本指針が衝突する場合は、実装前に衝突点と解決方針を明示する。

### 学びを目的に据える

**Ease of use is not the final goal. Better learning is.**  
**使いやすさは最終目的ではない。よりよい学びにつながることが目的である。**

**Make the tool easy to use; preserve the thinking that learning requires.**  
**道具の操作は分かりやすく。学びに必要な思考は大切にする。**

保存先や次の操作が分からない負担は減らす。一方、考える、自分の言葉で説明する、思い出す、誤りを見直すといった思考は、学習目的に応じて支える。操作を容易にすることと、学習上の課題を無条件に容易にすることを混同しない。例えば、解答をすぐ表示する操作は便利でも、考える前に答えを見て終わる設計になっていないかを検討する。

「操作の負担が減る → 教師が教材を見直す余裕ができる → 説明・練習・フィードバックが改善される → 理解や定着につながる」という関係は、各段階に仮説を含む。使いやすさ、学習する機会、学習成果を分けて評価する。クリック数、完了率、作成時間を、理解や定着の証拠と同一視しない。教師の作業負担を減らすことにも価値があるが、それだけで学習効果が高まったとは主張しない。

実証研究の環境がなくても、学習効果を設計仮説として意識する。既存研究を参照する場合は、出典、対象、条件と限界を確認し、この製品での効果を証明したものとして扱わない。常識や想像から得た仮説も、その由来と未確認部分を明示する。研究に基づく示唆、設計上の推論、操作の動作確認、実利用の観察、学習成果の評価を区別する。

ソフトウェアは、教師に唯一の「良い授業の型」を強制せず、説明・練習・確認・復習を用意しやすくする。成果は教材内容、学習者、授業運用にも左右される。観察できる環境がなければ仮説と設計点検を記録し、検証済みとせずに改善を進める。評価のための学習者追跡や新たなデータ収集を自動的に導入しない。

### 複雑さに見合う価値を求める

**Less complexity for teachers. More clarity for learners.**

**教師には余計な複雑さを減らし、学習者には分かりやすい道筋を。**

**Every feature must justify its complexity.**

**すべての機能は、それが生み出す複雑さに見合う価値を持たなければならない。**

これらは設計を導く原則であり、現製品ですべて達成したという主張ではない。新機能の追加だけでなく既存機能を残す判断にも適用する。想定する利用者と作業、減らす不要な判断、新たに増える概念や画面遷移、その釣り合いを裏づける証拠を記録する。操作や設定を増やす前に、削除・統合・表示整理・安全な既定値を検討する。

Moodleの機能、権限、アクセシビリティ、高度な設定への到達手段を保つ。公開範囲・提出・評価・期限の判断に必要な情報を残して操作負担を減らす。画面上の操作を減らすだけで単純になるとは限らない。重要な操作は見つけられる必要がある。

教材作成者の判断、学習者の現在地と次の行動、教師主導型と自律学習型への適合、標準Moodleとの整合性、操作体系の一貫性の5軸で評価する。同条件の作業を標準Topics・Boostと比較する。正確な版と構成を記録し、コード監査、開発者の操作確認、初見参加者の観察、学習成果の証拠を分ける。CI成功や開発者の慣れを参加者評価の代わりにしない。

変更ごとに「利用者・作業 → 観察された問題または仮説 → 価値と増える複雑さ → より単純な代案 → 証拠と未確認範囲 → 維持・簡略化・統合・削除・保留 → 次の受入確認」を記録する。これは開発上の判断記録であり、教師や学習者への入力フォームにしない。3プラグインそれぞれの独立した価値を保つ。

### 初心者への案内と熟練者の慣れた操作を両立する

**初めて使う人には分かる道筋を。慣れた人には滞りなく進める操作を。**

両者に配慮する。初見の迷いを減らしながら、Moodleの慣れた用語、標準の編集経路、高度な機能への直接的な到達手段を保つ。案内は必要なときに利用でき、読み飛ばしても進められるようにする。熟練者に説明の繰り返しや余分な手順を強制しない。習熟度別モードも、増える複雑さに見合う価値がなければ追加しない。

観察は、その文脈とともに扱う。初心者の「分からない」は調べるべき問題の証拠だが、それだけで全利用者に適した解決策が決まるわけではない。参加者の経験、作業、端末、受けた支援を記録し、個人の好みと繰り返し現れる問題を区別する。変更案を標準の操作と比較し、初心者の見つけやすさと熟練者の操作の継続性・効率をともに評価する。片方の利用者を観察できていなければ、その未確認範囲を明記する。

新たな経路や概念を増やす前に、ラベル、配置、既定値の改善や重複した操作の整理を優先する。慣れた操作であることだけを理由に、確認された障壁を残し続ける必要はない。変更が必要なら、その利点、覚え直す負担、標準機能への到達方法を記録する。一人の参加者に製品全体を最適化せず、両者の必要性の釣り合いを判断する。

### Dualの意味と製品の方向性

Dualは、教師が授業をする学びと、その場の教師の説明に頼らずMoodle上の教材で進める学びを指す。両者では説明、練習、確認、質問や返却の組み立てが異なる。それぞれを作りやすいコース設定と作成環境を提供する。「教師なし」は、教材作成者や採点・質問対応を行う支援者まで不要という意味ではない。

この二方式の構成支援の中心はCourse Formatである。Boostと標準活動でも成立させ、専用Themeへの依存で不足を補わない。初心者が目的から操作を見つけられることと、熟練者が標準の手順を維持できることを両立する。

Themeはデザイン性を重視する。標準形式でも価値を持ち、Course Formatと組み合わせるときは、その構成を理解して意図や優先順位を視覚的に明確にする。意味のある順序・階層・機能は変えず、配色、文字、余白、整列、強調、端末に応じた配置を整える。

学生側は、分かりやすく迷わない構成かを評価する。「楽しく学べる」を今回のシミュレーションで感情や学習意欲の測定へ置き換えない。Themeの美的な秩序は、配色とレイアウトの明示したルールへの適合と例外の理由で点検する。これを学習成果の証明とはしない。

まとまった同じ教材を二方式で実際に作り、学生としてたどる。Course Format＋Boost＋標準活動を標準Moodleと比較し、次に内容を固定してThemeを比較する。LessonMarkも標準形式＋Boostで単体を確認してから、影響する組み合わせを調べる。原稿の自動投入とUIでの教材作成を区別し、開発者のシミュレーションを初見利用者の評価に置き換えない。

## 2. 独立性

- 3プラグインを相互に必須依存として宣言しない。インストール、更新、基本機能の利用に、他の2つの導入を要求しない。
- Moodle本体やBoostなど、各プラグインが本来必要とする基盤への依存は、この相互独立性とは区別する。必要な依存と対応バージョンは正確に宣言する。
- LessonMarkは標準のコース形式とBoostでも、教材作成・閲覧・学習操作の基本機能が成立するようにする。
- course formatはLessonMark以外の標準活動でも、コース構成と学習の導線が成立するようにする。
- テーマは標準のコース形式・活動にも適用でき、他の2つがない場合も通常の表示と操作を保つ。
- 連携先がない、選択されていない、または対応機能を持たない場合は、その連携部分を省略するか標準の導線へ戻す。基本操作がエラーや行き止まりにならないようにする。

## 3. 責務の分担

| プラグイン | 主として担う責務 | 他の層へ委ねる責務 |
| --- | --- | --- |
| LessonMark | 教材の編集・保存・レンダリング、教材内の学習操作、教材の意味を保つ入出力 | コース全体の学習構成、サイト共通の外観 |
| format_duallearning | コース・単元の構成支援、学習形態に沿った進め方、活動間の導線 | 活動内部の教材処理、サイト共通の外観 |
| theme_duallearning | サイト共通の見やすさ、読みやすさ、端末に応じた配置、視覚的一貫性 | 教材データの意味や保存処理、進捗・成績・学習形態の判定 |

これは「CSSはすべてテーマ」という分担ではない。活動やコース形式は、自分が提供する操作の基本的な表示、スマホ対応、キーボード操作、アクセシビリティを自ら保証する。そのうえでテーマが余白、文字、色、全体の配置を調整する。

権限、公開範囲、完了条件などの機能的な判断を、テーマの表示切替やCSSによる非表示だけで実現しない。Moodleと該当機能の提供元を判断の主体とする。

## 4. 任意の連携による相乗効果

Moodleの活動情報、URL、完了情報、権限、File API、出力の仕組みなど、標準の接点を優先する。専用の接点が必要な場合は、提供側と利用側を明確にし、目的、対応範囲、不在時の動作を記録する。

- 他プラグインのクラスや関数を呼ぶ前に、その機能が利用可能であることを確認する。インストール済みであることだけを理由に、コースで選択済み・利用可能と仮定しない。
- 他プラグインの内部DBや非公開の実装を直接操作しない。教材、進捗、成績の正本を重複して持たない。
- 表示上の連携は、提供側が意味と用途を明示したクラスや属性など、安定した接点を優先する。DOMの偶然の階層、教材名、特定コースIDへの依存を避ける。
- 連携専用の接点を変える場合は、利用側への影響と旧版との組合せを確認する。3つの同時更新を基本機能の動作条件にしない。
- 一方を外したり別のテーマ・形式へ切り替えたりした際も、標準の運用の中で教材を利用し続けられるようにする。プラグインのアンインストールに伴うデータ削除は、Moodle標準の扱いと区別して説明する。

相乗効果は、学習者が次の活動へ迷わず進める、教材を読みやすくなる、教師の準備や案内の重複が減る、といった利用者の行動で説明する。単に3つを同時に導入できることを相乗効果とはしない。

## 5. 修正場所の判断例

| 問題・目的 | 最初に確認する場所と判断 |
| --- | --- |
| 標準Topicsのセクション移動でスマホ時に大きな余白が生じる | Moodle標準の出力とテーマの配置。使われていないcourse formatを変更して解決したことにしない |
| LessonMark本文の問題画像を、サイトの表示方針として広く見せたい | テーマの余白・表示幅。画像の意味や教材データは維持する |
| LessonMarkに画像拡大の操作を追加したい | LessonMarkの機能。専用テーマがなくても使えるようにする |
| PDF出力で目次が解答として扱われる | LessonMarkの教材解釈・出力処理 |
| Dual Learning形式が出力する活動間ナビゲーションが操作しづらい | course format自身の構造と基本表示。テーマによる補完だけで済ませない |

同じ症状でも、原因と影響範囲を調べてから責務を決める。複数プラグインの変更が必要な場合は、それぞれの変更理由と単独での効果を説明する。

## 6. 変更レビューと検証

変更説明には、次の判断を短く記載する。

1. 誰の、どの操作を改善するか。
2. なぜそのプラグインが修正を担うか。
3. 他の2つがなくても基本機能が成立するか。
4. 連携する場合、何が良くなり、不在・旧版の場合にどう動くか。
5. 確認した組合せと、確認していない範囲は何か。

学習や作成体験に関係する変更では、次の短い記録も添える。指針を教師向けの必須入力フォームへ変換しない。

| 問い | 記録すること |
| --- | --- |
| どの負担を減らすか | 操作上の迷い、重複作業など |
| どんな学習行動を支えるか | 考える、試す、説明する、思い出す、振り返るなど |
| 期待するつながりは何か | 負担の軽減から学習行動・成果までの仮説と前提。効果として断定しない |
| 逆効果はないか | 答えの早見、重要情報の隠蔽、形式的な完了など |
| 今、何を確かめられるか | 動作確認、設計点検、実利用の観察、学習成果の評価を区別し、未確認部分を残す |

基準となる単独構成は、LessonMark＋標準形式＋Boost、標準活動＋Dual Learning形式＋Boost、標準活動＋標準形式＋Dual Learningテーマである。これらと、変更で影響する2つの組合せ、3つ全部の構成から必要な範囲を選んで検証する。

連携の接点を変更した場合は、連携先がない構成と該当する組合せを必ず確認する。表示・操作の変更では、スマホ・PC、長い名称、キーボード、実際の利用者権限を考慮する。確認結果と未確認範囲を記録し、CI合格や特定テーマでの良好な表示を、他の組合せでも動作する証拠としない。

文書だけの変更に実行時の検査を一律に要求しない。検証は変更の影響に応じて選び、不必要な重複を避ける。

## 7. 文書の配置と更新

この共通指針は、3リポジトリそれぞれに英語版 `docs/DEVELOPMENT_PRINCIPLES.md` と日本語版 `docs/DEVELOPMENT_PRINCIPLES.ja.md` を置く。同じ言語の文書は3か所で同一内容とする。どのリポジトリだけを取得しても読めるようにし、特定のプラグインを他の上位に位置づけない。実行時に他リポジトリの文書を取得する仕組みは設けない。

- 原則を変更するときは文書改訂を上げ、日英両版と3リポジトリへ同じ変更を反映する。同時に反映できない場合は、未反映の言語・リポジトリを変更記録に明記する。
- 日英両版は同じ方針を表し、どちらか一方を上位としない。意味の不一致が見つかった場合は、合意済みの設計意図に照らして両版を修正し、改訂番号を揃える。
- 各READMEを入口にし、既存の開発・設計文書からも参照する。製品固有の詳細は各リポジトリの仕様書に記載する。
- 指針の変更は、それ自体でリリース済みZIPの差替え、バージョン変更、AWSへの反映を意味しない。
